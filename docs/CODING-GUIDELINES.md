# TunLatch Rust 代码规范与实践指导

适用范围：本项目的 Rust 程序、测试及系统接口封装。本文记录编码约定；工作区已经建立，当前实现状态与能力边界见 [README](../README.md)。

参考 [Google Rust Style Guide](https://google.github.io/styleguide/rustguide.html)，并结合 [需求文档](REQUIREMENTS.md) 与 [技术栈调研](TECH-STACK-RESEARCH.md) 制定。本项目是 Cargo 应用，按实际需要采用规则，不整体照搬其他代码库的制度。

## 1. 规则级别

- **必须**：影响保护正确性、内存安全、特权边界、错误可见性及自动检查的要求。
- **默认**：用于提高可读性的通常选择；具体情形采用其他写法更清楚时，可说明理由，不需要增加审批流程。
- 下文的项目专项要求属于本地约定，不能反向解释为 Google 原文的强制规定。产品行为以需求文档为准。

## 2. 从 Google 指南选用的原则

| 主题 | 本项目采用的原则 |
| --- | --- |
| 格式 | 用 rustfmt 保持一致，局部跳过应有具体理由 |
| 所有权 | 优先借用，按真实需求使用复制和共享所有权 |
| 接口 | 用类型表达易混语义，避免含义不明的布尔参数 |
| 错误 | 区分缺失与失败，优先模式匹配，说明异常原因 |
| 抽象与实现 | trait、泛型和宏按需引入，循环与迭代选择清楚的写法 |
| 安全与文档 | 隔离 unsafe，写清安全前提与接口契约 |

来源：[Google Rust Style Guide](https://google.github.io/styleguide/rustguide.html)。

不采用其中 Chromium 专属的禁用 async/await、特殊构建布局及测试框架；不引入 Fuchsia 专用同步类型。共享所有权和面向外部库的兼容性建议也不机械升级为本项目禁令。异步运行时采用 Tokio，并固定在工作区依赖中。

## 3. 格式、命名与代码组织

- **必须**使用项目选定的稳定工具链及 rustfmt，不为格式化引入 nightly。通常采用默认格式，100 列宽交由工具处理，不手工维护排版。
- **默认**按 Cargo 常规目录组织代码，模块围绕职责命名，避免泛化的 `utils` 堆积；按实际边界拆分，不为了“每个抽象一个 crate”增加结构。
- **默认**显式导入使用的项，避免在生产代码中用通配导入隐藏来源；测试中的 `use super::*` 和范围明确的第三方 prelude 可以采用。
- **默认**采用 Rust 标准命名与转换约定。类型名如 `TunnelId`、`PfStatus`，函数和模块使用 `snake_case`；路径保留 `Path` / `PathBuf`，不要过早转换为字符串。
- **默认**先使用具体类型、普通函数和固有方法；在确有替换实现或复用需求时再增加 trait、泛型或动态分派。常见 derive 宏可以正常使用。
- **必须**以第三方公开契约为依赖边界，不使用其标记为 `#[doc(hidden)]` 的内部接口；必要的系统绑定补充需明确维护归属和版本依据。

依据：[Rust 官方格式指南](https://doc.rust-lang.org/style-guide/) 与 [Rust API 命名约定](https://rust-lang.github.io/api-guidelines/naming.html)。

## 4. 领域类型与保护不变量

本节是针对防火墙需求的项目要求。

- **必须**区分用户配置的期望状态、PF 已提交的策略和实际观测状态；不能仅用一个 `enabled: bool` 同时代表三者。
- **必须**区分 TUN 内部地址、代理上游端点、网卡身份和规则标识。存在混淆风险时使用受约束的结构体或 newtype；同一底层类型的别名不能提供这种校验。
- **必须**区分“发现的候选 TUN”和“已确认可信的 TUN”。可信对象的构造要经过验证，公开字段、`Deserialize` 或 `Default` 均不能绕过验证；可通过受验证的转换实现反序列化。
- **必须**让保护状态的分支处理明确。未知状态、新增状态及第三方枚举的未知分支，不能默认解释为“已保护”或“允许直连”。
- **默认**用具名选项或模式表达有歧义的控制操作，避免 `apply_policy(true, false, true)` 一类调用。简单的查询结果仍可以是布尔值。
- **默认**输入只读数据时使用 `&str`、`&Path`、切片等合适视图；需要拥有配置快照或跨任务传递数据时，直接使用拥有所有权的类型，不为减少一次复制制造复杂生命周期。

类型设计参考 [Rust API 类型安全指南](https://rust-lang.github.io/api-guidelines/type-safety.html)，具体不变量来自本项目需求。

## 5. 错误处理与 panic

- **必须**将权限不足、PF 调用失败、网卡消失、配置无效和 IPC 断开等可预期运行情况通过 `Result` 或明确状态传递，不能依靠 panic 处理。
- **必须**保留足够信息以区分失败原因。领域和系统适配边界优先使用可匹配的错误类型，程序入口可增加 anyhow 上下文；不要让调用者靠匹配错误字符串决定是否解除阻断。
- **必须**处理关键返回值。不能用 `.ok()`、`let _ = ...` 或 `unwrap_or_default()` 将保护状态未知、规则提交失败等情况静默变成成功或空策略。非关键诊断允许尽力执行，但需明确这种性质。
- **必须**审查生产代码中的 `unwrap`、`expect`、断言及可能越界的访问。外部输入和运行环境错误不得触发这些路径；将 `unwrap` 改名为 `expect` 不能代替错误处理。
- **默认**对无法以类型表达的内部程序不变量，使用带原因的断言或 `expect`；不能将可恢复故障伪装为不变量。测试固定数据可以使用带上下文的 `expect` 和断言。
- **必须**明确恢复动作是否改变保护状态。错误被记录不等于已经恢复；发生部分完成或结果未知时，要保留原有保护或维持阻断并报告真实情况。

## 6. unsafe、FFI 与资源所有权

- **必须**将 PF ioctl、原生回调及必要的裸指针操作收敛在范围明确的系统适配代码中，业务层通过经过校验的安全接口调用；有合适的安全封装时优先复用。
- **必须**在每个 unsafe 块或相关不安全实现附近写 `SAFETY:` 说明，列明指针有效期、缓冲区长度、初始化、对齐、别名、线程或所有权中实际相关的前提，并指出由谁保证。
- **必须**为公开的 unsafe 函数说明调用方的安全义务；unsafe 函数体内的不安全操作仍使用显式 unsafe 块。采用 `unsafe_op_in_unsafe_fn` 检查。[Rust 2024 说明](https://doc.rust-lang.org/edition-guide/rust-2024/unsafe-op-in-unsafe-fn.html)
- **必须**在解析原生变长消息时校验长度、版本、边界和整数转换，不能先将任意字节解释成结构体，再补做检查。
- **必须**明确文件描述符、原生句柄、回调上下文和引用计数对象的所有者及释放时机。不能重复接管已有所有权的描述符，也不能让回调继续访问已经释放的上下文。
- **必须**遵守原生对象的线程限制。不能为了让对象进入 Tokio 任务而无依据地编写 `unsafe impl Send` / `Sync`。
- **必须**阻止 panic 经不允许展开的 FFI 边界传播。`catch_unwind` 如用于边界兜底，需符合 ABI 与 panic 策略，不能依靠它完成正常故障恢复或证明内存安全。[Rust FFI 指南](https://doc.rust-lang.org/nomicon/ffi.html)
- **必须**让 `Drop` 仅执行符合资源契约的清理。关闭 TUI 句柄、任务或控制连接时，不得通过析构隐式解除全局防火墙保护；显式停用操作与资源释放分开。
- **必须**让 PF 启停、提权和设备访问来自显式受控入口，不在程序加载或隐藏的初始化路径中触发这些副作用。

## 7. 异步、并发与任务退出

- **必须**让 PF 写入具有明确顺序，避免过期的异步结果重新放行已被较新决定阻断的出口。具体组织方式以实现需要为准，不强制引入 actor 框架。
- **必须**观察关键后台任务的退出和失败，不能丢弃任务句柄后假定服务持续健康。
- **必须**避免跨 `.await` 持有同步锁，阻塞的系统操作不得长时间占用异步执行线程。锁和共享所有权应围绕实际数据访问选择，不将每个对象统一包装成 `Arc<Mutex<_>>`。[Clippy 相关检查](https://clippy.rust-lang.org/stable/index.html#await_holding_lock)
- **必须**给外部操作和消息输入设置合理的超时、大小或队列上限；事件合并后应重新核对状态，不能因队列丢失或原生通知遗漏而推定可信。
- **必须**区分“客户端已断开”“任务收到取消”和“内核操作已结束”。PF 提交开始后，不能仅取消等待者就对外报告已回滚。
- **必须**明确关键任务如何通知退出、完成必要处理并等待结束。服务退出处理仍须遵守保护持续存在的需求。[Tokio 退出机制](https://tokio.rs/tokio/topics/shutdown)

## 8. 特权输入、配置与诊断

- **必须**在特权端重新校验 IPC 和导入数据，不因输入来自本机 TUI 就视为可信；限制消息长度、操作集合和目标资源。
- **必须**使用类型化参数调用系统工具，固定可执行路径，检查退出状态；不把配置、路径或界面输入拼接成 `sh -c` 命令。
- **必须**控制配置与恢复文件的路径、所有者、权限及替换流程；校验通过前不覆盖有效配置，不把写盘成功等同于 PF 生效。
- **必须**让启停、恢复及卸载只操作本项目持有的规则、配置和启用引用，不能把全局清空或停用作为通用清理方法。
- **必须**记录有助于定位故障的操作、策略版本、阶段和结果；不记录订阅内容、认证信息、密钥或完整敏感配置。日志失败不得造成保护被解除。
- **默认**注释解释副作用、错误、恢复边界和不显然的理由。公共接口及原生封装优先写契约，不复述函数名或基础语法，也不制造缺乏内容的文档注释。

## 9. 检查、测试与例外

基础检查采用以下命令；有互斥 feature 时分别验证受支持组合，不能为通过检查而静默跳过关键后端。

```sh
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --all-targets --locked
cargo test --workspace --doc --locked
```

- **必须**使用固定工具链获得可重复的格式和检查结果。依赖检查由 [deny.toml](../deny.toml) 与 CI 固定；新增 nextest、属性测试等工具前先确认与固定工具链兼容。
- **必须**对改变出口约束、可信绑定、状态迁移、权限校验或恢复行为的修改，提供相应的成功与失败场景证据；纯格式和简单文档修改不要求新增业务测试。
- **必须**区分模型测试、模拟 PF、真实内核验证和物理网卡抓包。前两者通过不能表述为已证明实机无泄漏。
- **默认**针对风险选择明确的 lint，如 `unsafe_op_in_unsafe_fn`、`unused_must_use`、`await_holding_lock` 和 `undocumented_unsafe_blocks`。不整体强制开启所有 `pedantic`、`nursery` 或 `restriction` 规则。
- **默认**将合理的 lint 例外放在最小作用域，写明原因；适合时使用 `#[expect(..., reason = "...")]` 使过期例外可被发现，不大范围关闭检查。[Rust lint 诊断属性](https://doc.rust-lang.org/reference/attributes/diagnostics.html)

工作区、固定工具链、格式/Clippy/测试/文档检查和依赖检查已经建立；完整检查顺序以 [CI 配置](../.github/workflows/ci.yml) 为准，上述命令不包含 release 构建和全部依赖检查。
